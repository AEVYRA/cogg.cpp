# Prior art and implementation choice — 2026-09-07

Author: Sofia, at Sasha's request. This is a targeted primary-source review, not
an exhaustive novelty search or a benchmark of competing implementations.

## Finding

**Yes: substantial parts of the proposed problem already have runtime-level
solutions.** Persistent agents, autonomous scheduling, transactional state,
resource accounting, causal execution journals and persistent KV caches each
have serious prior art. C++ and a single executable alone do not distinguish
cogg.cpp. “First OS for synthetic subjects” is not established.

I did not establish an existing implementation of the full Physalia contract in
one embeddable local inference runtime. That is an evidence gap, not proof that
no one has built it. The defensible project hypothesis is whether an explicit
subject successor boundary, coupled to persistent model-context ownership, gives
better recovery semantics and cognitive continuity than strong existing systems.

## What counts as a kernel solution

Three different levels must be separated:

1. **Host OS kernel:** process isolation, CPU scheduling, device memory. cogg.cpp
   is a user-space runtime; rewriting Linux is outside this project.
2. **Agent runtime kernel:** lifecycle, state authority, admission, journals and
   recovery enforced by the runtime rather than separately by every application.
3. **Inference engine:** tensor execution, model residency, context/KV lifetime.

A Python runtime can implement level 2 correctly. A C++ program can still contain
ad hoc application glue. Embedding a library is not inherently a workaround;
the deciding issue is who owns and enforces the relevant invariant.

## Closest systems

| System | Existing overlap | Boundary established in this review |
|---|---|---|
| AIOS | Kernel services for scheduling, contexts, memory, storage and tools | Kernel syscall scheduling is real architectural overlap. Its inspected scheduler handles resource requests; the complete Physalia successor transaction was not established. |
| Agent-libOS | Long-running AgentProcess, typed state, capabilities, durable runs, accounting, recovery | A close agent-runtime neighbor, including a shared transaction coordinator. Treat it as a serious reuse/baseline candidate. |
| OpenFang | Rust executable combining kernel, durable memory, agent lifecycle and autonomous background execution | Broad product-level overlap; inspected background modes are interval/cron/event based and session persistence has its own save path. |
| Letta | Agent identity/state across sessions, memory across conversations, background memory work | Already addresses the persistent-agent premise. Local inference-context ownership and our full atomic successor contract were not established. |
| LangGraph | Checkpoints, thread recovery, cross-thread stores | Durable graph execution is an architectural solution, not merely a caller's memory patch. |
| Temporal / Restate | Durable execution, persisted progress, waiting and resumption | Strong foundations/baselines for orchestration durability; model KV ownership is a separate concern. |
| llama.cpp | Native contexts and state/sequence save-restore APIs | Supplies inference primitives that cogg should reuse before considering a fork. |
| CachyLLama | C++ inference fork with persistent on-disk KV and compatibility checks | Direct prior art for persistence inside the inference engine; KV persistence cannot be marketed as our invention. |

### AIOS

The authors explicitly separate an AIOS kernel from its SDK. The code provides
resource-specific request queues and a round-robin scheduler. This is evidence
for a runtime service boundary, even though it is implemented in Python. The
repository also describes an early Rust scaffold; it must not be counted as a
finished port. [Repository](https://github.com/agiresearch/AIOS),
[paper](https://arxiv.org/abs/2403.16971),
[scheduler source](https://github.com/agiresearch/AIOS/blob/292d98f78c835499df18cdb6de6325bba1895862/aios/scheduler/rr_scheduler.py).

### Agent-libOS

The current project models an agent as a schedulable process and distinguishes
runtime authority from evidence records. Its storage contract uses typed
repositories sharing one transaction coordinator. It documents a single writable
Runtime per database, durable reservations and explicit recovery boundaries.
This is particularly close to the state-ownership problem; the fact that it uses
Python does not weaken that architectural relevance. The inspected documentation
does not establish our planned libllama context lifecycle or the Physalia
recognition/Crystal laws. [Repository](https://github.com/yingqi-z20/Agent-libOS),
[pinned storage contract](https://github.com/yingqi-z20/Agent-libOS/blob/72366eecc9e04cc7445a5ea51d7b5f236aa4d1e9/docs/storage.md).

### OpenFang

The architecture separates Rust kernel, runtime and SQLite memory crates.
Agents and sessions are restored at boot. In the pinned source, continuous and
periodic background tasks sleep for configured intervals; proactive operation
uses triggers. `SessionStore::save_session` writes conversation state with a
SQLite upsert. These observations do not prove the absence of stronger semantics
elsewhere in its code. I did not verify an atomic combination of model-proposed
wake, memory delta and a unique subject-chain successor. [Architecture](https://github.com/RightNow-AI/openfang/blob/acf2587e46be174c10200489c9a2d23a39a98aeb/docs/architecture.md),
[background execution](https://github.com/RightNow-AI/openfang/blob/acf2587e46be174c10200489c9a2d23a39a98aeb/crates/openfang-kernel/src/background.rs),
[session persistence](https://github.com/RightNow-AI/openfang/blob/acf2587e46be174c10200489c9a2d23a39a98aeb/crates/openfang-memory/src/session.rs).

### Letta and LangGraph

Letta describes a stateful agent as persistent identity with memory, model/tool
configuration and conversations. Its current memory documentation also supports
background “dreaming.” Therefore persistence across user sessions and background
reflection are not unique to cogg. The older sleep-time URL redirected to current
memory documentation during this review. [Stateful agents](https://docs.letta.com/concepts/stateful-agents),
[memory/dreaming](https://docs.letta.com/configuration/memory).

LangGraph distinguishes per-thread graph checkpoints from cross-thread stores.
A persistent checkpointer supports recovery; an in-memory saver does not survive
restart. This is a useful baseline for our durable projection mode. The durable
execution documentation URL redirected to the persistence page during this review.
[Persistence](https://docs.langchain.com/oss/python/langgraph/persistence).

### Durable execution and inference persistence

Temporal workflow execution and Restate's durable execution model are mature
architectural directions for preserving execution progress and resuming work.
They deserve comparison before inventing another external-action recovery
protocol. Neither source reviewed establishes native ownership of libllama KV
contexts. [Temporal](https://docs.temporal.io/workflow-execution),
[Restate](https://docs.restate.dev/foundations/key-concepts).

The pinned llama.cpp public header exposes context construction and sequence
state save/load/data operations. These support a library adapter; they do not
establish compatibility of arbitrary checkpoint files across versions/models.
[Public header](https://github.com/ggml-org/llama.cpp/blob/0cae43063cf15170e91a2ff4d034da0ecef4a1b2/include/llama.h).

CachyLLama documents SSD-backed KV checkpoints, hot/warm/cold tiers and model/
conversation compatibility checks. I inspected its current README, not a local
crash benchmark, so performance and recovery claims remain the authors' claims.
It is both a competitor for the caching portion and a source of lessons about
hybrid/recurrent model state. [Pinned README](https://github.com/SyntheticAutonomicMind/CachyLLama/blob/cea45f4222e1eea5c2c68388d7e75904a65b6778/README.md).

## Language decision and alternatives

**Selected for this implementation: C++20 runtime library and CLI, SQLite storage,
OpenSSL hashing; later a pinned libllama adapter.** CMake builds an ordinary library
and executable. This follows the supplied architecture's library-first route.

The practical reason is direct ownership of model/context handles and their
lifetime, with a small native dependency boundary. It is not a claim that C++
automatically makes persistence correct, scheduling autonomous or memory safe.
RAII, limited interfaces, transaction tests and sanitizers carry those obligations.

Other valid routes:

- Rust core plus llama C FFI: credible option with stronger default memory safety;
  costs an additional FFI ownership/toolchain boundary for this C++-oriented project.
- Build on Agent-libOS, Letta or OpenFang: faster route to a broad agent product;
  first establish whether their native state/extension contracts can represent the
  desired successor semantics and direct context lifecycle.
- Temporal/Restate/LangGraph orchestration plus a local inference service: strong
  durability baseline, especially for tools; different deployment and context
  ownership boundary from a compact embedded local runtime.
- Immediate llama.cpp fork: gives access to internals, but inherits model/backend
  maintenance. Defer until a measured limitation of the public API requires it.

Interfaces, analysis scripts and notebooks do not all need to be C++. They should
use a stable boundary when one is introduced. No Python service should be needed
merely to keep the core lifecycle alive.

## Corrections to the founding positioning draft

Replace broad promises with scoped, falsifiable contracts:

- “Crash-proof / resumes the exact thought” → completed subject transactions
  survive process restart; unfinished inference may be repeated and differ.
- “WAL beneath inference” → one runtime-owned transaction for the canonical state;
  a WAL by itself does not persist registers, pending outputs, KV or tool effects.
- “No OOM” → measurable admission and residency policy, once implemented. A native
  binary alone cannot guarantee it.
- “Python is fundamentally flawed / cron is fake autonomy” → identify the actual
  ownership, persistence and scheduling contract. Internal timers still need an
  executing process and do not demonstrate cognition.
- “First OS / 90% fewer bugs” → remove until a defined comparison supports them.

SQLite's atomic-commit and WAL documentation motivates the transactional boundary
and its storage assumptions; it does not warrant unlimited failure claims.
[Atomic commit](https://sqlite.org/atomiccommit.html), [WAL](https://sqlite.org/wal.html).

## Next empirical comparison

First demonstrate structural invariants independently of model quality; Phase 0
does that with a deterministic backend. Then compare the same model, tasks and
resource budget across semantic reconstruction, persistent token history and
persistent KV. Include a real existing durable runtime as baseline, not only a
deliberately weak stateless script.

Measure recovery boundaries, repeated work, duplicate external effects, time to
first useful continuation, prefill cost, VRAM/RAM and retention of task commitments.
For model-proposed wake timing, compare fixed/event-triggered timing with equal
compute budgets and predeclared task utility. Variable intervals alone prove only
that scheduling reacts to state, not that autonomous thought is useful.

Subject signatures, causal completeness, phenomenological subjectivity and
behavioral identity after model replacement remain separate questions. A hash
chain or a logical clock cannot by itself settle them.
